# 오스카 빌리지

O·S·C·A 네 집에 들어갔다가 빌리지로 돌아오는 이미지 기반 웹 앱입니다.

## 실행

프로젝트 폴더에서 실행합니다. Node.js가 필요하며 외부 패키지 설치는 필요하지 않습니다. 로그인과 투표에는 인터넷 연결이 필요합니다.

```powershell
npm start
```

브라우저에서 `http://127.0.0.1:5173`을 엽니다. 서버 종료는 터미널에서 `Ctrl+C`를 누릅니다.

## 화면 이동

- 메인 이미지에서 각 집의 현판과 문을 함께 포함하는 입구 영역을 클릭하면 해당 집으로 들어갑니다.
- 집 내부의 `마을로 돌아가기` 버튼을 누르면 메인 화면으로 돌아갑니다.
- 작은 화면에서는 이미지 아래의 집 선택 버튼도 사용할 수 있습니다.
- `Tab`으로 입구를 선택하고 `Enter`로 이동할 수 있습니다.
- 브라우저 뒤로 가기·앞으로 가기를 지원합니다.
- 마을과 하우스를 오갈 때 다음 배경 이미지를 준비한 뒤 180ms 페이드 아웃·300ms 페이드 인으로 전환합니다. 전환 중에는 클릭을 차단하며, 동작 줄이기 설정에서는 즉시 이동합니다.
- 방의 후보패널을 클릭하면 해당 방의 상세 보드가 팝업으로 열립니다.
- 클릭한 후보는 보드 상단에서 금빛 테두리와 `✓ 선택` 배지로 표시됩니다.
- 보드 상단의 다른 후보판을 클릭하거나 방향키로 후보를 바꿀 수 있습니다.
- 닫기 버튼, `Esc`, 팝업 바깥 클릭으로 방에 돌아갑니다.
- O·S·C·A 모든 후보 보드에 제공 PDF의 붉은 영역 소개를 표시합니다. 기존 A2z 폰트로 제목·부제·강조 문구·활동 목록을 표현하며 S의 하단 강조, C의 제목 옆 설명, A의 성과 지표도 포함합니다.
- 소개가 화면에 다 보이지 않으면 내용 영역에서 휠·터치·키보드로 세로 스크롤할 수 있습니다. 배경은 투명하고 스크롤바는 숨깁니다. 후보를 바꾸면 맨 위로 돌아갑니다.
- 소개를 스크롤할 수 있으면 오른쪽 아래에 움직이는 `↓` 버튼이 표시됩니다. 누르면 최하단까지 부드럽게 이동하며, 맨 아래에서는 `↑`로 바뀌어 다시 최상단으로 돌아갈 수 있습니다. 동작 줄이기 설정에서는 애니메이션 없이 즉시 이동합니다.
- 보드의 `투표하기`를 누르면 현재 선택한 후보의 투표 확인 팝업이 열립니다.

## 관리자

1. 개발 서버를 실행한 뒤 [관리자 페이지](http://127.0.0.1:5173/wic_admin)에 접속합니다. 일반 마을 화면에 관리자 링크는 표시하지 않습니다.
2. 지정한 관리자 비밀번호로 로그인합니다. 비밀번호는 DB에 bcrypt 해시로만 저장하며 화면 소스와 문서에는 포함하지 않습니다. 현재 OSCA 프로젝트의 설정·배포는 완료되어 직접 조작할 설정은 없습니다.
3. **대시보드**에서 총 참여자수(투표 1개 이상), 전체 가입자수(미투표 포함), 4개 투표 완료자수, 총 투표 건수를 확인합니다. 0~4개 투표 완료별 사용자수와 각 후보의 투표 건수는 막대그래프로 표시합니다. 그래프는 갱신할 때 부드럽게 나타나며 동작 줄이기 설정에서는 애니메이션을 생략합니다.
4. **사용자 · 투표 내역**에서 전화번호 뒷자리 또는 닉네임으로 검색합니다. 닉네임은 부분 일치, 영문은 대소문자 구분 없이 조회합니다. **전체 보기**로 검색을 해제합니다. 목록은 25명씩 조회하며 각 하우스의 후보·투표 시각(한국 시간)을 표시합니다. 작은 화면에서는 표를 좌우로 스크롤합니다.
5. 특정 하우스의 **삭제** 또는 사용자 행의 **전체 투표 삭제**를 누르면 대상과 삭제 범위가 표시됩니다. 선택적으로 삭제 사유를 입력한 뒤 **투표 삭제**를 눌러 확정합니다. **취소**·`Esc`로 닫으면 변경하지 않습니다. 삭제한 투표는 되돌릴 수 없지만 사용자 계정은 유지되며 삭제한 하우스에는 다시 투표할 수 있습니다. 일반 앱은 다시 접속하거나 탭으로 돌아오면 DB 현황을 갱신합니다.
6. 화면에서 확인한 투표와 실제 DB 기록이 달라지면 삭제를 중단하고 새로고침을 안내합니다. 삭제와 감사 기록을 같은 트랜잭션으로 처리하므로 감사 기록 저장에 실패해도 투표가 삭제되지 않습니다.
7. **새로고침**으로 최신 통계를 읽고, 작업이 끝나면 **로그아웃**합니다. 로그인 후 30분이 지나면 다시 로그인해야 합니다. 5분 안에 비밀번호를 5회 틀리면 5분간 로그인을 제한하며, 이 제한은 관리자 로그인 전체에 공통 적용됩니다.

관리자 세션은 `HttpOnly`·`SameSite=Strict` 쿠키에 보관하고 HTTPS에서 `Secure`를 적용합니다. 브라우저 저장소에 관리자 토큰을 저장하지 않습니다. Node 서버가 같은 출처의 요청만 중계하고, `osca-admin` Edge Function과 DB 함수가 관리자 세션을 다시 검증합니다. 관리자 로그인 없이 전체 사용자·통계 조회 및 삭제를 할 수 없습니다.

삭제 감사 기록을 확인하려면 Supabase의 **SQL Editor**에서 새 쿼리를 열고 아래 조회문을 실행합니다. 삭제 시각·전화번호 뒷자리·대상 하우스(`null`이면 전체)·삭제된 투표·처리 사유가 표시됩니다. 관리자 화면에서 감사 기록은 삭제할 수 없습니다.

```sql
select created_at, phone_suffix, house, deleted_votes, reason
from osca_admin.delete_audit
order by created_at desc
limit 100;
```

## 로그인과 투표

- 확인 팝업은 `예`에 기본 포커스를 둡니다. `예`는 저장, `아니오`·`Esc`는 저장 없이 보드로 복귀합니다.
- 하우스별 최초 투표만 저장하며 이후에는 `투표 완료`와 투표한 후보 번호를 표시합니다.
- 투표 안내의 하우스 명칭은 O `Outsight D.T`, S `서비스생산시스템`, C `컨설팅&엑셀러레이팅`, A `애자일`로 표시합니다.
- 저장 후 O→S→C→A 순서에서 첫 미투표 하우스로 이동을 제안하며 `아직 투표하지 않은 …로/으로 이동해 투표하시겠습니까?`로 안내합니다. `아니오`·`Esc`는 마을로 이동합니다.
- 네 하우스 모두 투표하면 완료 안내와 `마을로 돌아가기` 버튼을 표시합니다.
- 메인 화면의 `로그인 하세요` 또는 첫 투표에서 전화번호와 선택 닉네임을 입력합니다. 전화번호가 있으면 별도 안내 없이 기존 사용자로 로그인하며 닉네임은 DB에 저장된 값을 유지합니다.
- 전화번호는 국내 `010` 11자리만 받습니다. 공백·하이픈을 제거해 같은 번호로 처리합니다. 닉네임은 한글·영문·숫자 총 6자이며 중복을 허용합니다. 공백만 입력하면 미입력으로 처리하고 내부 공백·특수문자는 허용하지 않습니다.
- 메인 로그인은 투표 없이 사용자를 생성할 수 있습니다. 첫 투표의 신규 사용자는 최종 확인의 `예`에서 사용자와 투표를 하나의 DB 트랜잭션으로 생성합니다. 취소하면 둘 다 생성하지 않으며, 저장 실패에도 둘 다 취소됩니다.
- 이미 투표한 사용자가 첫 투표 경로로 로그인하면 `이미 투표 결과가 있습니다`와 최초 후보 번호를 안내합니다. 추가 투표와 변경은 DB에서도 차단합니다.
- 사용자 정보만 브라우저의 `osca.user.v1`에 저장합니다. 투표 결과는 Supabase DB에서만 읽고 저장합니다. 기존 `osca.votes.v1`은 폐기하며 DB로 이전하지 않습니다.
- 방문 시 로컬 전화번호를 DB에서 확인해 자동로그인합니다. DB 닉네임을 로컬에 갱신하며 닉네임 불일치는 로그인을 막지 않습니다. 조회 성공 후 사용자가 없을 때만 로컬 사용자 정보를 삭제합니다. 연결 실패 때는 유지하고 `다시 시도`를 제공합니다.
- 다른 브라우저에서도 같은 번호로 로그인하면 같은 DB 투표 결과를 사용합니다. 로그아웃·닉네임 변경 기능은 제공하지 않습니다.
- 로그인 후 우측 상단에 마젠타 핑크 닉네임(미입력 시 전화번호 뒷 4자리)과 얇은 `님 안녕하세요` 문구를 표시합니다. 작은 화면에서는 이미지 위에 표시합니다.
- 인사 문구를 누르면 `나의 투표 현황` 팝업이 열립니다. DB를 다시 조회해 O·S·C·A별 후보와 한국 시간 기준 투표 시각을 보여주며, 미투표는 `미투표`·`—`로 표시합니다. 조회 중·실패 상태도 표에 구분해 표시합니다. 닫기 버튼·`Esc`·바깥 클릭으로 닫을 수 있습니다.
- 투표 완료한 집은 마을 입구의 네온 민트 현판과 모바일 집 선택에서 구분됩니다. 방 안에서는 투표한 후보 패널 바로 위에 네온 완료 표시와 후보 번호를 표시합니다.

## Supabase 연결

Peter-Sung 조직의 서울 리전 OSCA 프로젝트를 생성해 연결했습니다. 프로젝트 ID는 `cisfvzotckftsyqodxud`입니다. 테이블·권한·트랜잭션 함수와 `osca-api` Edge Function을 배포했고 `config.js`에 공개 API 주소를 반영했습니다. 현재 추가로 직접 설정하거나 API 키를 복사할 작업은 없습니다.

전화번호 입력만으로 로그인한다는 합의에 따라 Supabase Auth 문자 인증을 사용하지 않습니다. 사용자는 `Authentication → Users`가 아니라 `public.osca_users`에 저장됩니다. 승인한 설정대로 이 API는 JWT 검사 없이 호출되며 모든 웹 출처의 요청을 허용합니다. 전화번호를 아는 사람은 해당 사용자의 닉네임·투표 결과를 조회하고 아직 투표하지 않은 하우스에 투표할 수 있습니다.

브라우저의 테이블 직접 접근과 공개 API의 전체 사용자 목록 조회는 차단합니다. 비밀 키는 Edge Function 서버 환경에만 있고 `config.js`에는 공개 주소만 있습니다. 사용자·투표 테이블과 관리자 전용 테이블에는 RLS를 켜되 공개 정책을 만들지 않았으므로 Advisors에 정책이 없다는 정보 항목이 표시될 수 있습니다. 이는 서버 전용 접근을 위한 의도된 구성입니다.

### 데이터 확인 단계

1. [OSCA Dashboard](https://supabase.com/dashboard/project/cisfvzotckftsyqodxud)를 열고 Peter-Sung 계정으로 로그인합니다.
2. 프로젝트 이름이 **OSCA**인지 확인하고 왼쪽 메뉴의 **Table Editor**를 선택합니다.
3. 스키마를 **public**으로 선택한 뒤 **osca_users**를 선택합니다. `id`는 사용자 ID, `phone`은 정규화한 전화번호, `nickname`은 선택 닉네임, `created_at`은 생성 시각입니다.
4. **osca_votes**를 선택합니다. `user_id`는 사용자 ID, `house`는 O·S·C·A, `candidate`는 후보 번호, `voted_at`은 저장 시각입니다. 사용자의 `id`와 투표의 `user_id`를 비교하면 같은 사용자의 투표를 확인할 수 있습니다.
5. SQL로 한 번에 확인하려면 왼쪽 **SQL Editor**에서 새 쿼리를 열고 아래 조회문을 실행합니다. 조회만 하므로 데이터는 변경하지 않습니다.

```sql
select u.phone, u.nickname, v.house, v.candidate, v.voted_at
from public.osca_users u
left join public.osca_votes v on v.user_id = u.id
order by u.created_at desc, v.house;
```

### 연결 오류 확인 단계

1. OSCA Dashboard 왼쪽에서 **Edge Functions**를 선택합니다.
2. 목록의 **osca-api**를 선택합니다.
3. **Invocations** 탭에서 요청 시각·응답 상태·소요 시간을 확인합니다. `200`은 정상 응답, `400`은 입력 오류, `503`은 서버 연결·설정 오류입니다.
4. **Logs** 탭에서 해당 시각의 실행 오류를 확인합니다. API는 전화번호·닉네임·비밀 키를 로그에 기록하지 않습니다.
5. 앱에서는 `다시 시도`를 누릅니다. 저장 요청의 응답이 끊겼다면 DB를 재조회해 이미 저장된 최초 투표를 확인하므로 중복 저장하지 않습니다.

메뉴 안내는 2026-10-04의 [Supabase 테이블 문서](https://supabase.com/docs/guides/database/tables)와 [Edge Function 로그 문서](https://supabase.com/docs/guides/functions/logging)를 확인했습니다.

### 다른 환경에 배포할 때

- 같은 OSCA DB를 사용할 때는 화면 파일과 `config.js`를 함께 배포합니다. 서버 비밀 키를 프런트엔드에 넣을 필요가 없습니다.
- 다른 Supabase 프로젝트를 사용할 때는 `supabase/migrations/`의 SQL을 적용하고 `supabase/functions/osca-api/`를 배포한 뒤 `config.js`의 `apiUrl`을 그 프로젝트의 함수 주소로 변경합니다. 현재 프로젝트에 이미 적용한 SQL을 다시 실행하지 않습니다.
- `supabase/config.toml`의 `verify_jwt = false`는 승인한 전화번호 입력 로그인 방식에 필요한 설정입니다.
- 관리자 기능까지 배포할 때는 HTTPS와 관리자 서버 중계가 필요합니다. Vercel에서는 아래 서버 함수 구성을 사용합니다. 일반 Node 호스팅에서는 `server.mjs`·`admin-proxy.mjs`를 실행하고 HTTPS 프록시가 외부 출처의 `Host`와 `X-Forwarded-Proto: https`를 전달하도록 설정합니다. 현재 개발 서버는 로컬 주소에만 연결됩니다.
- 관리자 서버 함수는 `supabase/functions/osca-admin/`입니다. JWT 검사 대신 자체 관리자 세션을 검증하며 브라우저 직접 호출용 CORS는 제공하지 않습니다. 다른 프로젝트에 옮길 경우 마이그레이션·관리자 함수 적용 후 그 프로젝트의 관리자 비밀번호 해시를 별도로 설정해야 합니다.

### Vercel 배포와 관리자 404 해결

기존 정적 배포는 `/admin.html` 파일만 제공하며 로컬 `server.mjs`의 `/wic_admin` 경로와 관리자 API를 실행하지 않아 404가 발생합니다. HTML 경로만 연결해서는 로그인까지 동작하지 않습니다.

`vercel.json`은 `/wic_admin`을 관리자 HTML로, `/wic_admin/api/:action`을 `api/wic_admin/[action].mjs` 서버 함수로 연결합니다. `npm run build`는 공개 화면·이미지 17개만 `dist`로 복사합니다. 서버 소스·문서·SQL·테스트는 정적 배포에서 제외됩니다. 이미지는 CDN에서 제공하고, 관리자 요청만 Vercel Node 함수가 기존 Supabase API로 중계합니다. 관리자 비밀번호와 Supabase 비밀 키를 Vercel 환경 변수에 넣을 필요는 없습니다.

1. 수정 소스가 GitHub `Peter-Sung/osca`의 `master`에 반영된 뒤 [Vercel Dashboard](https://vercel.com/dashboard)에서 **osca-vote** 프로젝트를 엽니다.
2. **Settings → Build and Deployment**에서 프로젝트의 **Root Directory**가 저장소 루트인지 확인합니다. `vercel.json`과 `package.json`이 있는 위치가 루트여야 합니다.
3. 배포 설정은 저장소의 `vercel.json`에서 **Framework Preset = Other**, **Build Command = npm run build**, **Output Directory = dist**로 지정했습니다. 이 설정은 프로젝트의 해당 설정을 덮어쓰므로 정상적으로 구성 파일을 읽으면 별도로 변경하지 않아도 됩니다. 빌드 로그에 `공개 파일 17개를 dist에 생성했습니다.`가 표시되는지 확인합니다.
4. **Deployments**에서 새 커밋의 배포를 선택하고 **Ready**가 될 때까지 확인합니다. 이전 커밋을 다시 배포하면 수정이 적용되지 않습니다. 새 배포가 자동 생성되지 않으면 Git 연결과 배포 브랜치가 `Peter-Sung/osca`·`master`인지 확인합니다. 새 커밋의 배포를 다시 실행할 때는 **Redeploy**를 사용합니다.
5. **Production** 도메인이 새 배포를 가리키는지 확인한 뒤 [운영 관리자](https://osca-vote.vercel.app/wic_admin)를 새로고침합니다. 지정 비밀번호로 로그인해 대시보드·사용자 검색을 확인합니다.
6. 화면이 404이면 새 커밋과 Root Directory·설정 파일 반영 여부를 먼저 확인합니다. 로그인 요청이 404이면 배포 상세에서 `api/wic_admin/[action].mjs` 함수가 생성되었는지 확인합니다. 503이면 Vercel의 **Logs**와 Supabase **Edge Functions → osca-admin → Invocations / Logs**에서 동일 시각의 응답을 확인합니다. 로그에 관리자 비밀번호나 쿠키 값을 직접 기록하지 않습니다.

위 설정 안내는 [Vercel 빌드 설정](https://vercel.com/docs/builds/configure-a-build), [프로젝트 구성](https://vercel.com/docs/project-configuration/vercel-json), [Node 함수](https://vercel.com/docs/functions/runtimes/node-js/advanced-node-configuration)의 공식 문서를 확인했습니다. 로컬 `npm run build` 성공만으로 운영 Vercel의 로그인 성공을 확인한 것은 아니므로, 재배포 후 별도 검증이 필요합니다.

## 파일

- `asset/` — 제공된 원본 배경 이미지.
- `index.html`, `styles.css`, `app.js` — 화면 및 이동 동작.
- `vote-store.js`, `vote-store.test.cjs` — DB API 호출·사용자 로컬 저장·자동로그인·오류 복구 및 테스트.
- `config.js` — 공개 Edge Function 주소.
- `supabase/migrations/` — 사용자·투표 테이블, 제약·권한, 원자적 저장 함수.
- `supabase/functions/osca-api/`, `api.test.mjs` — 서버 입력 검증·DB 호출과 테스트.
- `admin.html`, `admin.css`, `admin.js` — 관리자 로그인·통계·검색·삭제 확인 화면.
- `admin-proxy.mjs`, `supabase/functions/osca-admin/`, `admin.test.mjs` — 관리자 쿠키·인증·서버 중계와 테스트.
- `supabase/tests/admin.sql` — 임시 트랜잭션에서 관리자 집계·검색·삭제·재투표·실패 복구를 검증하고 롤백하는 SQL.
- `server.mjs` — 허용한 화면 파일·공개 설정·이미지 제공 및 관리자 API 중계 서버.
- `build.mjs`, `vercel.json`, `api/wic_admin/[action].mjs` — 공개 파일 빌드·Vercel 경로와 관리자 서버 함수.
- `plan.md`, `checklist.md`, `context-notes.md` — 계획과 진행 기록.
